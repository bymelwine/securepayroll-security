# Sécurité

- **Authentification.** Le service PHP vérifie les empreintes Argon2id. L’embauche génère un mot de passe temporaire qui expire et doit être changé avant l’accès aux fonctions métier. La boîte d’envoi locale conserve les invitations en clair dans des fichiers privés à usage de démonstration. Restreindre leur accès et leur rétention. Le limiteur tient compte du compte et de l’adresse, et les formulaires sensibles utilisent des jetons CSRF.
- **Autorisations.** Les rôles applicatifs et leurs permissions contrôlent les actions et la portée des données. PDO active les rôles MySQL de la requête via une liste fermée. Les opérations d’administration, de sauvegarde et d’audit disposent de comptes séparés. Certaines procédures s’exécutent avec les droits de comptes propriétaires verrouillés.
- **Chiffrement.** Les champs pièce d’identité, CNSS et RIB sont chiffrés par PHP en AES-256-GCM. Une seconde clé produit les index aveugles HMAC-SHA256. Conserver les deux clés privées hors base et hors dépôt. La protection porte sur les champs sélectionnés.
- **Audit.** Les événements applicatifs sont écrits dans un journal local et, lorsque disponible, dans la piste SQL en ajout seul. Des déclencheurs SQL complètent les événements sur les opérations sensibles. L’application journalise les échecs de persistance de l’audit. Pour une enquête, corréler les horodatages, les acteurs, les refus et les modifications de privilèges.
- **Durcissement.** Le lanceur privé utilise un socket Unix sans réseau MySQL, ignore la configuration système et désactive les opérations fichiers et `LOCAL INFILE`. Le serveur HTTP intégré est réservé au développement local.
- **Sauvegarde.** `bin/backup.py` crée un export logique privé via un compte dédié. Indiquer explicitement le socket de l’instance visée. Vérifier le manifeste et le marqueur `EXPORT_COMPLETE`, puis utiliser `bin/backup-crypt.py` pour chiffrer l’export en AES-256-GCM avec une clé distincte. Protéger aussi l’export intermédiaire et les journaux copiés.
- **Restauration.** Restaurer d’abord sur une instance isolée. Vérifier le manifeste, rétablir les comptes propriétaires, rôles et droits nécessaires, puis vérifier la lecture des champs chiffrés avec les clés correspondantes. Le dump applicatif ne contient ni les comptes MySQL ni les clés. La recette `tests/backup-recovery.py` contient la procédure de vérification.

Avant partage, lancer `python3 bin/audit-secrets.py` dans le dépôt local et examiner les candidats et l’historique. Signaler une anomalie en privé aux mainteneurs du dépôt et expurger les données sensibles du rapport.
